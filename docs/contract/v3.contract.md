# Acceptance contract: Jet Fighters v3 (TMS1370 rebuild)

Authored from `docs/prd/jet-fighters-v3.md` before decomposition. This is the
contract the cold exit verifier executes against the assembled v3 product. Its
sha256 is recorded at freeze; a mid-run edit aborts the run rather than
certifying against a moved target.

The class is `interactive`, as v2's was, and for the same reason: no cold agent
can judge whether the tube looks like the tube. What changed is the machine
underneath it, so almost every tier-1 criterion moved even where its intent did
not.

## What this contract is guarding against

Three failures, each with a name and a precedent in this repository.

### A facade that scores points

v1 shipped 100% merged and was, in the owner's verdict, a facade: it rendered a
convincing scope, so every process signal read "done". v2's contract encoded the
fix - **each tier-1 criterion must be falsified by an artifact that merely looks
finished** - and it held. Criteria here lead with a positive requirement that
absence cannot satisfy. V9 is the sharpest case: "the HMCS44 toolchain is gone"
is satisfied by an empty repository, so V9 also requires the TMS1370 core to be
present in the built bundle.

The rebuild adds a second facade shape v2 could not have: **a TMS1370 in name
that behaves like the HMCS44 it replaced**. Three concrete shapes, each with a
criterion that fails it on *capability* rather than on the ROM's use of it:

| Shape | Caught by |
| --- | --- |
| A sequential program counter | V2's LFSR bijection (core) and V1's ordinal-vs-offset comparison (assembler) |
| A four-deep subroutine stack | V2's "CALL inside a subroutine saves no return address" |
| An unbounded output vocabulary | V4's requirement that the core's O write path be **structurally** indexed by 5 bits |

That third row is the one this contract got wrong on its first draft: asserting
32 entries in the listing and closure over what the ROM drives leaves a core
whose `TDO` writes an arbitrary 8-bit mask entirely green, because the ROM we
authored never leaves the table. Closure tests the program; only the core test
tests the machine.

### Criteria narrower than the hardware

`docs/evidence/open-questions.md` §3b records v2's contract failing correct work
twice:

- **V1** asserted "highest assembled address <= 2047" against a 2048+128-word
  HMCS44 ROM whose upper 128 are the pattern region. A correct ROM defining a
  BCD score table writes there, and a verifier taking the maximum of the address
  column would have failed it.
- **V5** asserted "the burst is shorter than 150 ms". The bound itself is sound -
  `audio-reference.md` records missileFire as `< 150 ms (measured ~20 ms)`. What
  failed was the *method* the criterion implied: first-to-last edge **was** the
  burst against the bootstrap ROM, but against the full game the same window
  holds several sounds, so it read 445 ms where the isolated burst measures
  40.9 ms. A correct ROM failed a correct bound.

Both faults are the same mistake: something true of the artifact in front of the
author - an address ceiling, a measurement method - promoted to a property of the
machine. Three consequences here.

Every numeric bound below is either a hardware constant that cannot move
(2048 words, 128 nibbles, 9 grids, 12 plates, 32 PLA entries) or a **band read
from `docs/evidence/audio-reference.md` at verification time** - never a duration
or rate observed once and generalised. Where the evidence gives two figures for
one event, the criterion names which.

Where R6 leaves the instruction rate provisional, V10 requires provenance and
named constants rather than asserting a value the run is explicitly not entitled
to. MAME's 350 kHz is a fitted RC-oscillator approximation carrying a stated
±50 kHz spread, so "58 kHz" is a midpoint of 50-66.7 kHz and appears nowhere as a
threshold.

And **a criterion that waits on a timed game event owns its own drive.** The
machine falls silent unattended after a measured `UNATTENDED_SILENCE_S = 20.6`
seconds (`tools/probe/game-lifetime.test.ts`), so a criterion waiting on a
~19.8 s battleship cadence must inject input across the whole window or it will
fail a correct build. V8b states its input schedule for that reason. This is the
same fault as the two above, and the first draft of this contract committed it in
the criterion that announces the fix.

### The gate defect, which is still live

§3c records that `validate_completion.py` consults tier-1 failures when deciding
a verdict and never tier-3, while `_is_signed()` treats any non-empty
`operator_signoff` as assent. A **failed tier-3 criterion plus a sign-off object
therefore certifies `PASS`** - the exact escape hatch tier-3 exists to close.

This was re-checked against toolkit 1.56.0 while authoring this contract:
`_tier_failures` is called for tier 1 and tier 2 only. The defect is live. It is
a floor artifact in the plugin, not fixable from this repository, so v3 defends
against it in two ways instead:

1. **The run's own recording rule, binding regardless of the validator's return
   value.** The `tier3_escalations` entry naming `V12` is present in **every**
   state, and `operator_signoff` is absent in every state **except** a
   favourable observation. Both halves are load-bearing, because
   `AWAITING-TIER3-SIGNOFF` is derived from a non-empty `tier3_escalations` array
   (`tier3_awaiting = bool(record.get("tier3_escalations")) and not signed`), not
   from a tier-3 failure. Three states, three shapes:

   | State | `result` | escalation entry | `operator_signoff` | Verdict |
   | --- | --- | --- | --- | --- |
   | Not yet observed | `escalated` | present | absent | `AWAITING-TIER3-SIGNOFF` |
   | Observed, favourable | `pass` | retained | present | `PASS` |
   | Observed, rejected | `fail` | **retained** | **absent** | `AWAITING-TIER3-SIGNOFF` |

   Two shapes certify `PASS` on a build the operator rejected, and both are
   forbidden. **`result: fail` with no retained escalation entry** certifies,
   because `_tier_failures` is consulted for tiers 1 and 2 only. And
   **`operator_signoff` written to record a rejection** certifies, because
   `_is_signed()` treats any non-empty object as assent - a sign-off whose text
   reads "rejected" is still assent to the validator. A rejection is recorded by
   *withholding* the sign-off, never by writing one that says no.
2. **The tier-3 surface is paired, not sole.** Every perceptual claim in V12 that
   can be observed mechanically has a tier-1 twin (V5 for the display's address
   space and PWM, V8 for the audio bands, V10 and V14 for cadence provenance), so
   a mis-recorded tier-3 cannot be the only place a regression hides.

## Blocked artifacts are recorded, never skipped

Four requirements gate on MAME romset artifacts nobody in this project has yet -
`tms1100_common2_micro.pla`, `ginv.svg`, `tms1100_ginv_output.pla` and `mp2110`.
The PRD names this the top-line risk.

**No criterion is conditional on an artifact arriving.** Instead, the three
criteria that need one - V6, V11 and V13 - each state in their own observation
that an absent artifact is recorded `result: undriven` with that reason. That
instruction has to live in the criterion, not only here: a cold verifier reading
"`ginv-addressing.md` exists and records..." against a missing file records
`fail`, and `fail` outranks `partial` in the validator's precedence, so the whole
position would collapse to `FAIL` on a run that is merely blocked.

The distinction being preserved is real and worth the words. **Absence of the
artifact is a blocked run; a hand-invented addressing is a failed one.** They
must not read alike in the record.

**The ceiling this run can reach should be understood before it starts.** With
the romset absent, `PASS` is unreachable by design - v3 built on an invented
segment addressing is not v3. If only `ginv.svg` is missing, V6 is the single
blocked criterion and the ceiling is `PARTIAL`. If nothing arrives, R0 blocks
R1/R2/R5 and the run fails outright. Launched knowing that, a `PARTIAL` or
`AWAITING-TIER3-SIGNOFF` record is the correct outcome rather than a
disappointment.

## Drive surface

Tier-1 criteria are driven in Node, not a browser, because `src/machine/` never
touches the DOM. v2's probe harness carries forward and its JSON field names are
unchanged, but three of its values mean something different on this machine and
v3 must update it accordingly:

`tools/probe/machine-probe.ts`, runnable as
`npx vite-node tools/probe/machine-probe.ts [--cycles N] [--input SPEC] [--emit-edges]`,
writing a single JSON object to stdout:

```
{
  "romWords":     int,           // assembled program words, 8-bit, program region only
  "ramNibbles":   int,           // RAM high-water mark, <= 128
  "strobeCycles": int,           // machine cycles executed (one per six oscillator pulses)
  "gridsStrobed": [int],         // distinct display-grid R lines (R0-R8) driven; excludes the
                                 //   R9/R10 input strobes and R15 speaker, which share the latch
  "snapshots": [
    { "atCycle": int, "litSegments": [[grid, plate, duty], ...] }
  ],
  "speakerEdges": [[cycle, level], ...]   // R15 transitions, when --emit-edges; there is no D port
}
```

That `gridsStrobed` comment matters. On the HMCS44 the grids sat on a separate D
port, so "R lines driven" and "grids driven" were the same set. On the TMS1370
the display grids, both input strobe columns and the speaker are all R latch
bits, so a probe reporting R lines honestly would return 9, 10 and 15 alongside
the grids. The field is display grids specifically.

`snapshots[0]` is a baseline taken once the machine has completed at least one
full display sweep and before any input is injected; it is always present. Each
`--input` event appends one further snapshot taken after that event has been
strobed in.

`--input SPEC` takes `name=value@cycle` (e.g. `lever=up@120000`, `fire@120000`)
and injects the control through the K matrix exactly as the case wiring does -
K1/K2/K4 returned from a strobe on R9 or R10, K8 unstrobed for fire - not by
poking game state.

**Cycle counts in the actions below mean something different from v2's.** One
instruction per six oscillator pulses at ~350 kHz is roughly 58,000 machine
cycles per second against v2's 400,000, so v2's `--cycles 400000` bought about
one second and here buys about seven. Where a criterion needs only "at least one
full sweep", a generous round figure is given and any refinement of the
oscillator constant leaves it generous. Where a criterion waits on a **timed game
event**, the figure is stated as the interval it must cover and recomputed from
R6's constant rather than copied - a rate refinement would otherwise silently
truncate the window and fail a correct build.

## Floors, and why they sit where they do

- **>= 200 assembled program words** of 2048. Far below a real game program, far
  above any stub.
- **>= 600 passing tests.** The tree holds ~1287 static `it`/`test` sites. That
  figure is not a survivor count and should not be read as one: v3 deletes 226 in
  `tools/hmasm/`, rewrites ~370 under `src/machine/cpu/`, and R4's re-addressing
  and R5's six re-derivations reach most of `src/machine/board`,
  `src/machine/tube` and `tools/probe` besides. Genuinely untouched is closer to
  190. The floor is set where a rebuilt core, assembler and probe suite clear it
  comfortably while a gutted repository cannot - not where existing tests carry
  it.
