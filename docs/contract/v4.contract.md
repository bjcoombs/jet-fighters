# Acceptance contract: Jet Fighters v4 (pace, and the cells two things stand on)

Authored from `docs/prd/jet-fighters-v4.md` before decomposition. That PRD is
built on measurements rather than on a survey: the owner's skill-3 clip, timed
by two pipelines that share no code, and four blanking windows of
`IMG_6113.mov`. This contract is what the tasks derived from it are graded
against. Its sha256 is recorded at freeze; a mid-run edit aborts the run rather
than certifying against a moved target.

The class is `interactive`, for the reason v2's, v3's and v3-entities'
contracts give: "does it feel right when you play it" is the question the pace
work exists to answer, and a cold agent cannot judge it. What differs from
`docs/contract/v3-entities.contract.md` is scope. This contract does not
re-litigate the missile rank, the jet model, the entry position or the TMS1370
core. It covers five things: how fast the shot crosses a column, how fast the
squadron marches and whether its ladder is coherent, how long the march note
lasts and how much of the display that darkens, whether a shot and a jet on one
cell is a hit, and one property v3-entities stated wrongly.

**F1 supersedes v3-entities criterion E1's freeze on `MISSILE_LO` and
`MISSILE_HI`.** That freeze is not reversed by assertion: E1 froze the speed on
the survey's measurement that "at 125 ms a column or faster a defending player
wins in 60-107 seconds at every skill", and F5 re-measures exactly that, on a
machine that has since gained a per-lane rank and lost `jm_capture`'s lane
condition. `v3-entities.contract.md` itself is not edited. It is frozen, and E1
stands as written for the run it graded.

## What this contract is guarding against

### A pace change that moves one number and breaks the game it was measured on

The missile at 9 sweeps and the squadron at four times its current rate are two
changes to the same quantity: how long a player has to react. Each is defensible
alone and the pair is what gets played. F5 is a criterion rather than a note for
this reason - a build can satisfy F1 and F3 exactly and be unplayable, and the
survey that froze the missile speed in the first place says so in as many words.
F5 is deliberately two-sided: a build that becomes trivially winnable fails it
just as a build that becomes unwinnable does.

### A floor repair that contradicts the pace it is repaired beside

`step_reload` writes `STEP_HI` = 0 at skill 3 with four kills - sixteen sweeps,
325 ms, below the 488 ms floor its own constants document - and a fifth kill
floors it back to 32, so the descent is not monotonic
(`docs/evidence/open-questions.md` section 18). **Repairing the borrow while
leaving `STEP_HI_MIN` at 1 would forbid the pace F3 requires**, because 32
sweeps measures 689 ms at skill 3 against a clip whose slowest reading is 467
ms. F3 and F4 are therefore written so that the floor's *value* is F3's to set
and the *shape* of the descent is F4's to fix: F4 asserts that nothing is
written below `STEP_HI_MIN`, whatever `STEP_HI_MIN` then is, and that the
descent is monotone. A contract that pinned the floor at 488 ms and the pace at
300 ms would be satisfiable by no build at all, which is the defect this run is
paying to avoid repeating.

### A note lengthened until it stops being the note

The blanking that F2 is about is the speaker parking the sweep, so lengthening
the note buys dark frames directly. That makes the dark-frame fraction a
temptingly cheap thing to move and a bad thing to move alone. F2 therefore binds
the note's own emitted duration to the band the evidence holds, requires both
floors to **rise** rather than be adjusted in either direction, and requires the
note to stay outside the harmonic comb range that identifies
`open-questions.md` section 15's device tone - a note stretched to 410 ms would
buy the fraction and become a different sound.

### The one v3-entities got wrong, and the shape of the error

E4's third conjunct required "the rocket's lane sequence unchanged by varying
only the fire-press timing". That contradicts E4's own first conjunct. Press
timing feeds `NIB_ENT`, `NIB_ENT` feeds the entry position, entry position feeds
which lanes are occupied, and `rf_look` stops the rotor only on an occupied
lane, so press timing legitimately moves the sequence on a machine that
satisfies PRD R5. Measured: at skill 3 with the lever in lane 2, the first
launch had only lane 0 occupied and fired down lane 0. Occupancy forced it.

The property E4 was reaching for is what the v2 defect would actually violate: a
lane taken from a free-running timer nibble knows nothing about the squadron, so
it fires into empty lanes. F7 states that as the per-launch occupancy falsifier
`tools/probe/tms1370-rom.test.ts` already asserts, plus the read-site closure
that today exists only as a comment beside it. **The occupancy half of F7 passes
on the current build and is not what F7 is buying**; the closure half has no
test anywhere in the tree, and a nibble is exactly the thing this project has
already had one extra reader creep into.

### Two coincidence classes that are one class

A plane that spawns onto a live shot is not hit by it (`open-questions.md`
section 14: 30 spawn coincidences, 6 escapes, measured). A shot fired onto a jet
already standing at grid 5 in that lane is not hit either, and the jet captures
the launcher before the missile walk next runs (PR #191's census). F6 requires
both to be closed and to be closed **the same way**, because a rule that hits
one and not the other makes the outcome depend on which of two writes inside one
sweep happened first, which is the machine state `jet_enter`'s header already
calls a trap for every probe written afterwards.

**The run's base commit is the merge commit of PR #194**, the commit that put
this contract on `main`. It is a resolved sha at verification time, not a
merge-base of branches that no longer exist: resolve it with

    git log --format=%H --grep='(#194)' -1 main

and call the result BASE. Every diff in this contract runs from BASE to HEAD.
F1 diffs it for scope containment and for the suite's skip and `it.fails` counts,
F3 and F7 for `v3-entities.contract.md` being unmoved, F2 for the blanking floors'
starting values, F6 for the spawn-escape census, and the evidence-band conjunct
below for every band. A commit landing on `main` between authoring and
verification moves BASE forward with it, which is the point: the scope-containment
diff then covers this run's work and not somebody else's.

**The bands are read from documents this run also rewrites, so they are pinned
too.** F2, F3 and F6 each require editing a section of `docs/evidence/` that
holds a band another conjunct is checked against, and only this contract's bytes
are sha256-frozen. Each of F1, F2, F3 and F6 therefore carries the same
conjunct: any band it reads that differs from the at-time-of-writing figure
stated in this contract is accompanied, in the same document, by the
re-measurement and the command that produced it, visible in `git diff BASE HEAD`. A band widened in the commit that failed to hit it fails
the criterion that reads it.

**Black-box rule.** `CLAUDE.md`'s first section governs every criterion here.
Nothing may consult the dumped MP2110 ROM image, MAME's driver internals for
Gakken Invader / Tandy Fire Away / Galaxy Invader, or any disassembly or
write-up of that program, as a source of game behaviour. A verdict reached that
way is not a verdict this contract accepts.
